## X1 — No evidence download capability exists at all (new finding, real gap)

**STATUS (2026-08-17, commit `b336953`): CLOSED, verified live.** Real
`GET /api/cases/{case_id}/evidence/{evidence_id}/download` route added
(`src/external/routes/cases.py`), gated identically to the existing
`list_case_evidence` read route, streaming real bytes via
`S3EvidenceStorage.stream_object()` (never a presigned-URL redirect, so
the new `EVIDENCE_DOWNLOAD` audit event stays synchronous with the real
access). Verified end-to-end (`poc/evidence_download/`) against real
MinIO and a real Postgres: byte-for-byte match, correct headers, a real
audit row, and correct 404 handling for not-yet-promoted/cross-org/
nonexistent evidence. Along the way, caught and fixed a real bug in the
route's own first draft (an un-awaited coroutine passed to
`StreamingResponse`) before it was ever committed, and surfaced (without
fixing, per the same discipline W8 already established for this exact
issue) a real, pre-existing `quota_held` column drift on the shared dev
Postgres. 1948→1954 tests (+6), independently re-verified.

**Confirmed by direct code read, not from `PROGRESS.md`:** `EvidenceStorage.stream_object()`
(`src/adapter/storage/storage.py`/`s3.py`) is called only from
`src/application/parsing_orchestration.py` and `evidence_intake.py` —
internal parsing/hashing/scanning paths. **No route anywhere calls it for
a user-facing download.** `src/external/routes/evidence.py` has upload,
finalize, retry-intake, retry-parse, start-parsing, delete, and
legal-hold routes — no download route at all.

**Real consequence:** an analyst using KronOS today has no way to
retrieve the original evidence file bytes through the application — only
its extracted timeline records via search. For a forensics platform,
this is a real, user-facing capability gap, not just a missing audit
event. This is *why* `Static_Compliance_Pentest_Review.md`'s COMP-11
("no `evidence.download` audit event type exists") was findable in the
first place — the capability was never built, so of course no audit
trail exists for it.

**Fix:** a real `GET /api/cases/{case_id}/evidence/{evidence_id}/download`
route, gated the same way `list_case_evidence` already is (any
authenticated org member with real case access — `get_tenant_context` +
`assert_case_access`, all four roles including `READ_ONLY` per the
permission matrix's own "read" tier, not restricted to
ORG_ADMIN/CASE_LEAD/ANALYST), streaming `stream_object(evidence_key,
bucket="evidence")`'s real bytes back (reuse the existing streaming
idiom already used internally, per CLAUDE.md §A.5 — never buffer the
whole file in memory) with the evidence's own real filename/content-type.
Every real download logs a new `EVIDENCE_DOWNLOAD` `AuditEventType`
(closing COMP-11 for real) via the existing `AuditLogService`, with
`actor_user_id`/`actor_username`/`evidence_id`/`case_id` — mirroring
every other mutation/access route's own audit-on-action discipline.

**Priority: P0** — real, user-facing capability gap + a genuine ISO
A.5.28 compliance gap (full custody trail including reads), zero external
infra needed, well-scoped, no design ambiguity.

## X2 — Two already-decided "adopt now" verdicts were never implemented

**X2a (Postgres streaming replication) STATUS (2026-08-17): CLOSED, verified
live.** `charts/kronos/values.yaml`'s `postgresql:` block now sets
`architecture: replication`, `readReplicas.replicaCount: 1`,
`replication.synchronousCommit: "on"` + `numSynchronousReplicas: 1` (real
config key confirmed against the resolved `bitnami/postgresql` chart
**18.8.9** — `helm dependency build` re-run fresh this pass, matched the
prior attempt's own finding). `values-dev.yaml` explicitly overrides back
to `architecture: standalone` (dev doesn't need it, confirmed via
`helm template` that dev renders only the primary). `docker-compose.prod.yml`
gained a real `postgres-replica` service (`pg_basebackup -R` bootstrap,
`docker/postgres/replica-entrypoint.sh`) and a one-shot
`postgres-replication-init` job (mirrors the existing `keycloak-init`
pattern) that flips the primary into synchronous mode only after the
replica is confirmed streaming.

**Real, materially important finding along the way, not assumed from V10's
verdict text alone:** baking `synchronous_standby_names` into the primary's
config at cold boot deadlocks the primary's own first-boot database
bootstrap (confirmed against both the vanilla `postgres:16-alpine` image
*and* the real `bitnami/postgresql` image via direct `docker run` — see
`poc/postgres_replication/README.md` "real finding #2"), because that
bootstrap is an ordinary client transaction requiring a synchronous ack
from a standby that cannot exist yet. Fixed by deferring the sync-mode flip
to after the replica is confirmed healthy (`synchronous_standby_names` has
`context=sighup`, reload-safe, empirically confirmed against the pinned
image). This same caveat is now documented in `charts/kronos/values.yaml`
and `docs/deployment.md` for the Helm/first-install path, which has no
equivalent one-shot-job mechanism wired up in this pass (no real k8s
cluster available to verify a Helm hook Job against; `helm lint`/
`helm template` output confirmed the values render correctly, which is the
honestly-reachable subset of "verified" without a cluster).

Verified end-to-end in `poc/postgres_replication/` (real primary + real
replica, real data written to the primary appearing on the replica, real
`pg_stat_replication.sync_state=sync`) — twice: once against the PoC's own
throwaway compose, once again directly against the real, committed
`docker-compose.prod.yml` + `docker/postgres/*` files (see that PoC's
`output.txt` PART 3). No application code changed (V10's own claim
confirmed, not just repeated). 1954/1954 tests unaffected (no `src/`
change).

Both `docs/POSTGRES_MINIO_HA_RESEARCH.md` (V10) and
`docs/REDIS_BLAST_RADIUS_RESEARCH.md` (W5) concluded real, specific,
low-risk infrastructure changes should be adopted now:

- **Postgres streaming replication** (V10 §6.1 verdict) — **X2a CLOSED
  2026-08-17, see this section's own STATUS note above.**
- **Redis DB-role separation** (W5 §6.1 verdict) — **STATUS (2026-08-17,
  commit `d7a99e9`): CLOSED, verified.** `docker-compose.prod.yml`'s single
  `redis:` service split into `redis-auth-streams` (DB0 step-up + DB3
  stream-ingest) and `redis-celery` (DB1 broker + DB2 result backend), each
  with its own volume, own password, own real healthcheck (a real
  pre-existing gap — the original single `redis:` service had no
  healthcheck at all despite `kronos-backend` depending on it via
  `condition: service_healthy` — was found and fixed as a direct byproduct
  of this work). `charts/kronos/Chart.yaml` gained a second aliased Bitnami
  `redis` dependency (`redis-auth-streams`/`redis-celery`, real Bitnami
  chart 28.0.5, `helm dependency build`-confirmed); `values.yaml`/
  `values-dev.yaml` updated to match. Verified via
  `poc/redis_role_separation/`: raw `redis-cli` cross-instance isolation
  (writes to one instance genuinely invisible on the other, distinct
  `run_id`s confirming separate processes) plus stronger evidence —
  real `RedisTicketStore`/`RedisStreamIngestAdapter` app classes
  constructed against the split topology, all round-trips and isolation
  checks passing. `helm lint`/`helm template` independently re-run and
  confirmed clean, both aliased subcharts rendering as distinct resources.
  1954 passed/2 skipped before and after (true no-op delta — zero `src/`
  changes, matching W5's own "zero application code changes needed"
  finding). Independently re-verified by the orchestrator (not just the
  subagent's self-report) before merge.

Both verdicts were explicit, reasoned, and — per their own research —
cheap (Postgres: enable the existing Bitnami chart's `readReplicas`
support; Redis: `src/config.py` already models every role as an
independent DSN, so splitting is purely a deployment-topology change, no
application code needed). This is the same class of "researched,
decided, never executed" gap this initiative's own discipline exists to
close.

**Priority: P1 each** — real, already-decided, no design ambiguity
remaining, but genuine infrastructure changes needing real verification
(a real replica actually replicating, a real split-Redis topology
actually serving the right roles) before being called done, not just a
`values.yaml` edit.

## X3 — Real browser-level Keycloak login has still never been exercised

`PROGRESS.md` §3.2 flagged this in July; Milestones W7/W14 added real
Playwright infrastructure and captured real screenshots, but both used a
mocked-API harness specifically because `kronos.local` wasn't reachable
in *that* sandbox at the time. Worth a real attempt now that Playwright is
an established part of this repo's toolchain — `kronos.local` does
resolve on this host (used by many prior PoCs against the real dev
stack). If a real login-through-Keycloak-through-the-real-app flow can be
captured, that closes a real, long-standing verification gap; if it
still can't (e.g. a sandbox networking constraint), that's worth
confirming and documenting honestly rather than re-guessing next time.

**Priority: P2** — real gap, but lower urgency than X1/X2, and higher
uncertainty about feasibility in this environment.

**STATUS (2026-08-17): CLOSED, verified live.** `kronos.local` **was**
reachable from the dispatched agent's own environment (same host as the
orchestrator, not a separately networked sandbox) — confirmed directly
(`curl -sk https://kronos.local/` → `HTTP 200`, `getent hosts kronos.local`
resolving via the static `/etc/hosts` entry), so the real attempt went
ahead rather than being blocked. A real Chromium browser
(`playwright` 1.61.0, no mocked routes anywhere in the script) was driven
through the genuine flow: unauthenticated `/cases` → real redirect to
`/login` → "Sign in with SSO" → real 302 to Keycloak's real hosted
`/realms/kronos/.../auth` endpoint (genuine PKCE `code_challenge`) → real
credentials (`case-lead` / `DevCaseLead#2026`, **pre-existing**, seeded by
`docker/keycloak/kronos-realm.json` — not newly created) typed into
Keycloak's real login form → real redirect chain back through nginx,
landing authenticated on `/cases` with real, org-scoped case data
rendered (`kronos-dev` org alias in the header) → session confirmed to
persist navigating to `/detections` → real access-token claims decoded via
the app's own `/auth/refresh` cookie proxy (`sub`, `roles=['case-lead']`,
`acr=aal1`, `organization={'kronos-dev': ...}`, real `iss` pointing at
`kronos.local:8443/realms/kronos`) → real sign-out back to `/login`. 10/10
checks passed. Real screenshots and the real captured transcript are in
`poc/keycloak_browser_login/` (`README.md`, `run_poc.py`, `output.txt`,
`screenshots/`).

**Real, actually-hit (not speculative) `CERTIFICATE_VERIFY_FAILED` along
the way:** the step-ca leaf cert had already expired (`expire date: Aug 8
23:09:44 2026 GMT` against a run date of 2026-08-17) — confirmed via
`urllib.request.urlopen` raising the literal
`[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get
local issuer certificate`. Per CLAUDE.md's narrow, pre-authorized recovery
for this exact symptom, ran `docker compose -f
docker/docker-compose.dev.yml up -d tls-init && docker restart
docker-nginx-1` (nothing else) and confirmed a fresh leaf cert
(`expire date: Aug 18 13:58:03 2026 GMT`) before proceeding.

**Real, minor finding surfaced along the way (documented, not fixed — out
of scope for this verification-only task):** the real access token minted
for `case-lead` carries `preferred_username: null` and `email: null`, so
`frontend/src/components/Layout.tsx`'s `{user.username}` renders empty in
the header (only the org alias shows, e.g. `/ kronos-dev` with nothing
before it) — visible in `poc/keycloak_browser_login/screenshots/
3_authenticated_cases_dashboard.png`. Doesn't change this gap's outcome
(`sub`/`roles`/`acr`/`organization` are all real and correctly populated,
and real org-scoped case data rendering is itself stronger session
evidence than a username string), flagged for a future pass since it
wasn't previously known.

**Also worth noting for the record:** `poc/evidence_sse_realtime/
browser_verify.py` (commit `22c9739`, 2026-07-29, already on this branch
before this pass) had already, incidentally, driven a real Keycloak
browser login with the same credentials/selectors while verifying an
unrelated SSE bug — it just was never credited as closing this specific
gap. This pass's capture is an independent, fresh, dedicated re-run (not a
reference to that one), and the two are mutually consistent.
