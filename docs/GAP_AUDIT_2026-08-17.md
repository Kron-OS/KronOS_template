## X1 — No evidence download capability exists at all (new finding, real gap)

**Confirmed by direct code read, not from `PROGRESS.md`:** `EvidenceStorage.stream_object()`
(`src/adapter/storage/storage.py`/`s3.py`) is called only from
`src/application/parsing_orchestration.py` and `evidence_intake.py` —
internal parsing/hashing/scanning paths. **No route anywhere calls it for
a user-facing download.** `src/external/routes/evidence.py` has upload,
finalize, retry-intake, retry-parse, start-parsing, delete, and
legal-hold routes — no download route at all.

**Real consequence:** an analyst using KronOS today has no way to
retrieve the original evidence file bytes through the application — only
its extracted timeline records via search. For a forensics platform,
this is a real, user-facing capability gap, not just a missing audit
event. This is *why* `Static_Compliance_Pentest_Review.md`'s COMP-11
("no `evidence.download` audit event type exists") was findable in the
first place — the capability was never built, so of course no audit
trail exists for it.

**Fix:** a real `GET /api/cases/{case_id}/evidence/{evidence_id}/download`
route, gated the same way `list_case_evidence` already is (any
authenticated org member with real case access — `get_tenant_context` +
`assert_case_access`, all four roles including `READ_ONLY` per the
permission matrix's own "read" tier, not restricted to
ORG_ADMIN/CASE_LEAD/ANALYST), streaming `stream_object(evidence_key,
bucket="evidence")`'s real bytes back (reuse the existing streaming
idiom already used internally, per CLAUDE.md §A.5 — never buffer the
whole file in memory) with the evidence's own real filename/content-type.
Every real download logs a new `EVIDENCE_DOWNLOAD` `AuditEventType`
(closing COMP-11 for real) via the existing `AuditLogService`, with
`actor_user_id`/`actor_username`/`evidence_id`/`case_id` — mirroring
every other mutation/access route's own audit-on-action discipline.

**Priority: P0** — real, user-facing capability gap + a genuine ISO
A.5.28 compliance gap (full custody trail including reads), zero external
infra needed, well-scoped, no design ambiguity.

## X2 — Two already-decided "adopt now" verdicts were never implemented

Both `docs/POSTGRES_MINIO_HA_RESEARCH.md` (V10) and
`docs/REDIS_BLAST_RADIUS_RESEARCH.md` (W5) concluded real, specific,
low-risk infrastructure changes should be adopted now — neither has
actually been implemented, confirmed by direct grep:

- **Postgres streaming replication** (V10 §6.1 verdict): zero
  `readReplicas`/`streaming replication`/`standby` references anywhere in
  `charts/kronos/values.yaml` or `docker/docker-compose.prod.yml`.
- **Redis DB-role separation** (W5 §6.1 verdict): `charts/kronos/values.yaml`
  still has exactly one `redis:` block (single instance, all four roles
  still multiplexed); `docker-compose.prod.yml` still has exactly one
  `redis:` service.

Both verdicts were explicit, reasoned, and — per their own research —
cheap (Postgres: enable the existing Bitnami chart's `readReplicas`
support; Redis: `src/config.py` already models every role as an
independent DSN, so splitting is purely a deployment-topology change, no
application code needed). This is the same class of "researched,
decided, never executed" gap this initiative's own discipline exists to
close.

**Priority: P1 each** — real, already-decided, no design ambiguity
remaining, but genuine infrastructure changes needing real verification
(a real replica actually replicating, a real split-Redis topology
actually serving the right roles) before being called done, not just a
`values.yaml` edit.

## X3 — Real browser-level Keycloak login has still never been exercised

`PROGRESS.md` §3.2 flagged this in July; Milestones W7/W14 added real
Playwright infrastructure and captured real screenshots, but both used a
mocked-API harness specifically because `kronos.local` wasn't reachable
in *that* sandbox at the time. Worth a real attempt now that Playwright is
an established part of this repo's toolchain — `kronos.local` does
resolve on this host (used by many prior PoCs against the real dev
stack). If a real login-through-Keycloak-through-the-real-app flow can be
captured, that closes a real, long-standing verification gap; if it
still can't (e.g. a sandbox networking constraint), that's worth
confirming and documenting honestly rather than re-guessing next time.

**Priority: P2** — real gap, but lower urgency than X1/X2, and higher
uncertainty about feasibility in this environment.
