# PoC: full backend-only, end-to-end evidence lifecycle

## Versions
Same real stack as prior PoCs: `postgres:16-alpine`, `redis:7-alpine`,
`minio/minio:latest`, `opensearchproject/opensearch:2.11.1`, real
`celery==5.6.3` worker consuming the real queues from `celery_app.py`.

## What this actually does

Boots the real FastAPI app (real production startup path), starts a real,
separate Celery worker process consuming `q.index`/`q.parse.fast`/
`q.parse.plaso`, then drives the exact sequence
`docs/ingestion-pipeline.md` describes end to end over real HTTP + a real
presigned MinIO PUT with the real `tests/fixtures/samples/real/system.evtx`
sample:

```
POST /api/evidence/upload/request        (real presigned URL, real MinIO)
PUT  <presigned URL>                     (real bytes, real MinIO)
POST /api/evidence/upload/finalize/{id}  (real validate+scan+hash+promote)
  -> autonomous from here on, no client involvement:
  Celery dispatch_parse -> start_parsing() -> PARSING
  Celery parse_artefact_fast (FastEvtxParser, real evtx-rs) -> execute_parse()
  -> TimelineIngestionService.ingest_records() -> real OpenSearch bulk index
  -> COMPLETE -> finalize_evidence -> INGEST_COMPLETED audit event
```

Keycloak JWT parsing is **not** re-verified here — already thoroughly
covered in `poc/keycloak/` and `poc/multi_tenancy/` — so this PoC overrides
`get_tenant_context` to focus on the pipeline mechanics. Same reasoning for
ClamAV: `configure_clamav_from_settings()`'s real dev-mode fallback (no
clamd reachable -> `NoOpScanner`, a warning, not a mock I inserted) is
exercised as-is; the scanner itself is `poc/clamav/`'s job.

## Real finding: `ensure_index_template()` was dead code — the ECS mapping was never applied

First run: the pipeline completed successfully end-to-end (COMPLETE state,
full audit trail, hash chain intact) — but a query for the just-indexed
documents by `kronos.evidence_id` (a `term` filter, exactly the pattern
`OpenSearchQueryBuilder.org_id_filter` uses for `kronos.org_id`) returned
**zero hits**, while a bare `match_all` against the same index correctly
returned all 194 real EVTX records. Root-caused by checking the real
index's mapping directly:

```
"evidence_id": { "type": "text", "fields": { "keyword": {"type": "keyword", ...} } }
```

— dynamic mapping, not the `keyword`-typed field `src/adapter/opensearch/
index_template.json` declares. `grep -rn "ensure_index_template" src/`
confirmed it: the method exists in three places (the ABC, the real
`OpenSearchClient`, and the in-memory test double) and is **never called
anywhere else in the codebase** — same dead-code pattern as
`QueryIsolationGuard`/`OpenSearchQueryBuilder` found in `poc/multi_tenancy/`.
`ensure_ism_policy()` (a related but distinct OpenSearch concept — index
*lifecycle*, not field *mapping*) genuinely is called every time, so it was
easy to assume the sibling call was wired up too. It wasn't.

**Consequence, beyond just this PoC's query failing:** any exact-match
`term` filter against these string fields (a real search API, `DLS` role
`term` filters, or `OpenSearchQueryBuilder.org_id_filter` if that
class is ever actually wired up per `docs/subsystems/multi-tenancy.md`'s
"belt-and-braces" description) would silently match nothing against a
dynamically-mapped index — not a security leak, but a real, silent
functionality break, and one that's easy to miss because `match_all`-style
browsing (e.g. scrolling a raw OpenSearch Dashboards discover view) still
looks like everything's fine.

**Fixed** in `src/application/timeline_ingest.py`: added a
`_template_applied` guard, calling `ensure_index_template()` exactly once
per `TimelineIngestionService` instance, mirroring the existing
`_ism_applied`/`ensure_ism_policy()` pattern right next to it.
`TimelineIngestionService` is built fresh per Celery task (per
`celery_runtime.py`), so this runs on every ingest — harmless, since
`put_index_template` is a plain idempotent upsert (no "already exists"
handling needed, unlike the ISM policy's PUT).

Re-verified after the fix, against a freshly deleted+rebuilt index: the
real mapping now shows `"evidence_id": { "type": "keyword" }` directly (no
dynamic fallback), and the same `term` query that returned 0 before now
correctly returns all 194 documents.

## Incidental finding (not fixed here — deferred to `poc/chain_of_custody/`)

Running the full unit suite around a real local-midnight rollover on this
host (timezone `Europe/Paris`, UTC+2 in summer) surfaced 2 real,
reproducible failures in `tests/unit/test_audit_routes.py::TestMerkleProof`,
confirmed to fail identically with and without this PoC's change (i.e. not
a regression from `ensure_index_template()` — a pre-existing bug this PoC's
timing incidentally tripped over). Root cause, found in
`src/external/celery_app.py`'s `anchor_audit_log` beat task:

```python
yesterday = date.today() - timedelta(days=1)          # LOCAL server timezone
day_start = datetime(yesterday.year, yesterday.month, yesterday.day, tzinfo=UTC)
```

Every audit event's `occurred_at` is stored as `datetime.now(UTC)` (real UTC),
and `GET /api/audit/merkle-proof/{event_id}` scopes its lookup by
`target.occurred_at.date()` — the UTC calendar date. `date.today()` returns
the *local* calendar date. Whenever the server's local timezone is ahead of
UTC (as here) and the beat task runs in the roughly 2-hour window after
local midnight but before UTC midnight, `yesterday` computes the wrong day
relative to what the UTC-timestamped events actually group under, so the
anchor gets stored under (or looked up from) the wrong day — reproduced
directly: `date.today()` returned `2026-07-22` while `datetime.now(UTC)`
was still `2026-07-21` on this host at test time.

Deferred to `poc/chain_of_custody/` (Postgres → Merkle → RFC3161 →
kronos-attest) rather than fixed here, since it's unrelated to this PoC's
scope (the ingestion pipeline, not the daily anchoring job) and deserves a
real day-boundary test of its own rather than an ad-hoc one-line change.
