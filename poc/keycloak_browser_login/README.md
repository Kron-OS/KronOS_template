# PoC: real browser-level Keycloak login (Milestone X3)

## What this actually does

A real Playwright/Chromium browser (not the mocked-API harness Milestones
W7/W14 used) drives the genuine flow: `https://kronos.local/cases`
(unauthenticated) → real frontend redirect to `/login` → click "Sign in with
SSO" → real 302 to Keycloak's real hosted `/realms/kronos/.../auth` endpoint
(genuine PKCE `code_challenge`/`nonce`/`state`) → type real credentials into
Keycloak's real login form (`#username`, `#password`, `#kc-login`) → real
redirect chain back through nginx into the frontend, landing authenticated
on `/cases` with real case data rendered → navigate to `/detections` to
confirm the session persists → decode the real access token's claims via
the app's own real `/auth/refresh` cookie-proxy endpoint → real sign-out
back to `/login`.

No `page.route()` interception, no mocked responses, anywhere in this
script — every request Chromium makes crosses the real network to the real
containers.

## Reachability (confirmed directly, not assumed)

`curl -sk https://kronos.local/` → `HTTP 200` from this agent's own shell
(same host as the orchestrator's — this worktree runs directly on the host,
not a separately networked sandbox). `getent hosts kronos.local` resolves
via a static `/etc/hosts` entry (`192.168.5.13 kronos.local`), not DNS.

**Real, actually-hit `CERTIFICATE_VERIFY_FAILED`** (not speculative): the
step-ca leaf cert had already expired — `curl -v` showed `expire date: Aug
8 23:09:44 2026 GMT` against a run date of 2026-08-17, and
`urllib.request.urlopen('https://kronos.local/')` (no `-k` equivalent)
raised `[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable
to get local issuer certificate`. Per CLAUDE.md's explicit, narrow
authorization for this exact symptom, ran:

```
docker compose -f docker/docker-compose.dev.yml up -d tls-init
docker restart docker-nginx-1
```

Re-checked: new leaf cert `expire date: Aug 18 13:58:03 2026 GMT` (fresh,
within the real 24h TTL). The remaining `CERTIFICATE_VERIFY_FAILED` from
plain `urllib` after that (root CA not in the OS trust store) is expected
and is why this PoC's own script uses
`context.new_page(ignore_https_errors=True)` — the same pattern
`poc/evidence_sse_realtime/browser_verify.py` already established, not a
new workaround.

## Real, minor finding along the way (noted, not fixed — out of scope for this verification task)

`frontend/src/components/Layout.tsx` renders `{user.username}` in the
header, and `frontend/src/utils/parseTenantContext.ts` maps it from the
token's `preferred_username` claim — but the real token minted by this
realm for `case-lead` carries `preferred_username: null` and `email: null`
(confirmed above, not assumed). The header therefore renders only the org
alias (`/ kronos-dev`), with no username text before it — visible in
`3_authenticated_cases_dashboard.png`. This is a real, pre-existing gap
(either the realm's protocol mapper isn't emitting these claims, or the
frontend should fall back to `sub`), but CLAUDE.md's brief for this task is
explicit that `src/`/`frontend/` are not to be touched here — flagged for a
future pass, not fixed in this one. It does not change the outcome of this
PoC: `sub`, `roles`, `acr`, and `organization` are all real and correctly
populated, and the case-list content itself (real data, real org-scoped)
is independent, stronger evidence of a genuinely authenticated, tenant-scoped
session than the username string would have been.

## Teardown

Nothing container-side was created by this PoC (script runs a real
Chromium browser via `playwright`'s own managed binary, closed at the end
of the script; no new Docker containers). The one infrastructure action
taken (`tls-init` + `docker-nginx-1` restart) is a refresh of state already
owned by the running dev stack, not a new resource — nothing to tear down.
