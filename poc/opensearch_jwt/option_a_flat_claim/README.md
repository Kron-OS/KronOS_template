# PoC: flat-claim DLS templating (Option A) — CONFIRMED WORKING

Follow-up to `../README.md` result #2 (nested `organization` claim can't
drive DLS templating). This tests the natural fix: does `${attr.jwt.X}`
templating work for a **flat, top-level scalar** custom claim instead?

Deliberately Keycloak-free per the plan ("verify this works at all before
touching Keycloak") — JWTs are hand-signed with a throwaway RSA key
(`test_key.pem`/`test_pub.pem`, generated fresh for this PoC, no relation
to any real credential) so the claim shape can be controlled directly: a
flat `"org_id": "<string>"` claim, not Keycloak's nested Organizations
shape.

## Result: yes — and it eliminates per-org/per-user provisioning entirely

Real OpenSearch 2.11.1, security enabled, JWT authc configured against
the test key. **One** generic role (`kronos-generic-tenant`) with DLS
`{"term": {"kronos.org_id": "${attr.jwt.org_id}"}}` on `kronos-*` indices,
mapped **once, ever** to the broad `analyst` backend_role (not to any
specific org or user). Two real docs indexed via the real
`OpenSearchClient.bulk_index()`, one per org.

Three real hand-signed tokens tested:

| User | org_id claim | Provisioned specifically? | Real search result |
|---|---|---|---|
| user-a-sub | org-aaaa-1111 | — | `{doc-org-a}` only |
| user-b-sub | org-bbbb-2222 | — | `{doc-org-b}` only |
| user-a2-sub | org-aaaa-1111 (same org as user A) | **No — never touched, no new role/mapping created** | `{doc-org-a}` only |

The third row is the actual proof: a second member of org A, added with
**zero OpenSearch-side changes**, is automatically and correctly isolated
to org A's data purely because the DLS filter resolves `${attr.jwt.org_id}`
from their own token at query time.

## What this means for the production fix

Today's `ensure_tenant_role()` creates a **new role per org** and (per
`../README.md` result #3) never maps anyone to it. The verified
alternative here needs:
- **One** static OpenSearch role + DLS template, created **once**, ever
  (not per org).
- **One** static role-mapping (broad backend_role → that one role),
  created **once**, ever.
- A Keycloak protocol mapper emitting the user's org_id as a **flat**
  top-level claim (not nested `organization`) — the one piece not yet
  built/tested (needs real Keycloak Organizations integration — see the
  repo's ordered PoC plan, next step).

If that Keycloak-side piece works as expected, `ensure_tenant_role()`
becomes unnecessary — no backend code ever needs to call OpenSearch to
provision a new org or a new org member again. This is a materially
simpler and more scalable design than what's coded today, or than the
org-scoped-backend-role alternative (Option B) discussed earlier, which
still requires re-provisioning per org even if not per user.

## Follow-up: how to actually get a flat claim out of Keycloak — researched, not yet built

See `keycloak_mapper_research.md`. Read the real Keycloak 26.2.0 source
(not guessed): the built-in `oidc-organization-membership-mapper` cannot
emit the org **id** as a flat claim under any configuration — its
single-valued mode gives the org **alias** (still nested-free, but not the
UUID `kronos.org_id` needs), and its id-bearing mode is always nested one
level under the alias. The script-mapper path is a disabled-by-default
preview feature with an uncertain JS engine in the shipped image and is
rejected as disproportionate/risky for this. The verified path forward is
Keycloak's standard `oidc-usermodel-attribute-mapper` (the same category of
built-in mapper this repo's realm already uses for `roles`/`sub`) reading a
plain user attribute `org_id` set once per membership by
`scripts/provision_keycloak_org.sh` at the same point it already links org
membership. Next (step 3): wire this for real and re-run this PoC's setup
against a real Keycloak-issued token instead of the hand-signed test JWT.
