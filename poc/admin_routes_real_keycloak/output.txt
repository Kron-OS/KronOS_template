(the pytest test above only asserts status_code >= 400; this probe captures

REAL RESULT: remove_user(org-A-admin, cross-org target) -> HTTPException status_code=503 detail='Keycloak Admin API request failed'
cleaned up probe org/user

Finding (not a tenant-isolation bug -- the mutation is correctly blocked,
the org-B user remains a real member of org B afterward in both the pytest
test and this probe): remove_user's DELETE target
(/organizations/{tenant.org_id}/members/{user_id}) is already org-scoped by
construction, so Keycloak itself rejects a delete of a non-member with a
real 404. admin.py's _to_http_error() only special-cases 400->422 and
409->409; every other status (including this real 404) falls through to
the generic 503 "Keycloak Admin API returned server error" branch. The
isolation guarantee holds for real, but the surfaced error message
(503/"service unavailable") is misleading to an org-admin who just tried to
remove a user id that simply isn't in their org -- a real, if low-severity,
error-mapping imprecision worth a follow-up (see GAP_AUDIT_2026-08.md P1-15
V5 STATUS note).
