(exit code 2 -- the temp bootstrap server only listens on the Unix socket by
design; the REAL server, which would listen on TCP, never starts because
entrypoint is still blocked inside /docker-entrypoint-initdb.d bootstrap)

DIAGNOSIS: the postgres:16-alpine entrypoint creates the POSTGRES_DB database
("kronos") via a completely normal client transaction (`CREATE DATABASE`)
during its own bootstrap, before any replica can possibly exist yet. With
`synchronous_standby_names=kronos_poc_replica` and `synchronous_commit=on`
(Postgres 16's own default -- see PART 2 pg_settings query below) already
active at that point, CREATE DATABASE blocks forever waiting for a
synchronous ack from a standby that has never connected and, because the
primary is still stuck in bootstrap, never can. The primary bootstrap
process itself deadlocks. This is a real, general PostgreSQL fresh-cluster
bootstrap-ordering hazard, not a bug specific to this PoC's scripting --
confirmed against the exact pinned postgres:16-alpine image used by this
repo's docker-compose.prod.yml.

Real fix applied (see docker-compose.poc.yml comments + PART 2 below): boot
the primary WITHOUT synchronous_standby_names, let the replica bootstrap and
begin async streaming, then flip the primary into synchronous mode via
`ALTER SYSTEM SET synchronous_standby_names = '...'; SELECT pg_reload_conf();`
in a one-shot init job (real precedent already in this repo:
docker-compose.prod.yml's own `keycloak-init` service uses the same
one-shot-job pattern for a different bootstrap-ordering problem). Confirmed
empirically (real `pg_settings` query against this exact pinned image, not
assumed from memory) that this is reload-safe, no restart required:

$ docker exec pg-context-check psql -U postgres -tAc \
    "SELECT name, context FROM pg_settings WHERE name = 'synchronous_standby_names';"
synchronous_standby_names|sighup
$ docker exec pg-context-check psql -U postgres -tAc \
    "SELECT name, context FROM pg_settings WHERE name = 'synchronous_commit';"
synchronous_commit|user
$ docker exec pg-context-check psql -U postgres -tAc \
    "SELECT name, context FROM pg_settings WHERE name = 'wal_level';"
wal_level|postmaster

(kronos-poc-pg-primary torn down with `docker compose down -v` before
re-running with the fix; no leftover containers/networks/volumes.)
