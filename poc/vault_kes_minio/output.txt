--- 3. First KES boot attempt using docker/kes/kes-config.yml's ACTUAL
    field names (engine_path / key_name / retry) -- FAILED ---
Error: kesconf: invalid vault keystore: invalid transit config: no key name specified

GAP FOUND #2: fetched the real schema for this pinned KES tag directly
from github.com/minio/kes @ 2024-06-17T15-47-05Z (server-config.yaml):
  keystore.vault.transit fields are named `engine` and `key`, NOT
  `engine_path` / `key_name` as docker/kes/kes-config.yml has them.
  Also: KES's vault keystore in this version is fundamentally a K/V
  secrets-engine-backed keystore (fields: engine, version, prefix) with
  Transit as an OPTIONAL wrap-at-rest layer for what's stored in K/V --
  it is not "Vault Transit is the KMS backend" as the repo's comments
  and roadmap.md Prompt 5.2 assume. Required adding a `kv` v1 mount in
  Vault and `engine: kv / version: v1 / prefix: kes-keys` to the config,
  which the repo's kes-config.yml has no equivalent of at all.

GAP FOUND #5: used `MINIO_KMS_KES_CA_PATH` (the name roadmap.md's
Prompt 5.2 deliverable list literally specifies: "MINIO_KMS_KES_CERT_FILE,
MINIO_KMS_KES_KEY_FILE, MINIO_KMS_KES_CA_PATH"). Extracted strings from
the real minio/minio:latest binary:
$ strings /usr/bin/minio | grep KMS_KES
  ... MINIO_KMS_KES_CAPATH ... MINIO_KMS_KES_ENDPOINT ...
  MINIO_KMS_KES_KEY_FILE ... MINIO_KMS_KES_KEY_NAME ...
  MINIO_KMS_KES_CERT_FILE ... MINIO_KMS_KES_KEY_PASSWORD ...
  MINIO_KMS_KES_API_KEY ...
The real env var is `MINIO_KMS_KES_CAPATH` (no underscore before CAPATH).
roadmap.md's own deliverable spec names the wrong variable.

Also discovered along the way: certs signed by a bare self-signed
identical leaf-as-CA (my first cert-generation attempt) produced a TLS
handshake that "succeeded" per curl -v trace but KES's app layer still
returned "tls: client certificate is required" for MinIO<->KES -- a
proper CA-signs-leaf chain (root CA -> KES server cert, root CA -> MinIO
client cert) was needed for reliable mTLS; documented in run_poc.sh.
